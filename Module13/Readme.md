### Введение

У нас есть два сервиса: один про книги, другой про авторов. Пользователю нужна страница книги с инфой и об авторе. Без
агрегации фронтенду пришлось бы делать два запроса: сначала за книгой, потом за автором. Это медленно и неудобно.

Лучше сделать один умный эндпоинт в Gateway, который сам сходит в оба сервиса и вернет все вместе. Пользователь получит
сразу все нужное одним запросом.
Как это технически работает

В Gateway ставим Spring WebFlux с WebClient. Когда приходит запрос на /api/book-details/{id}, Gateway делает два
параллельных запроса: в BookService и в AuthorService.

Вот ключевой момент: делаем их не по очереди, а одновременно. Для этого используем Mono.zip(). Эта штука запускает оба
запроса параллельно и ждет, когда оба ответят. Как только оба ответа пришли, объединяем их в один JSON и отдаем
клиенту.
Почему параллельно, а не последовательно

Если делать по очереди: сначала книгу (100 мс), потом автора (150 мс), итого 250 мс.
Если делать параллельно: оба запроса одновременно, ждем самого медленного (150 мс), выигрыш почти 100 мс.

В реальности выигрыш еще больше, потому что сетевые задержки складываются.

### Что с ошибками

Один из сервисов может лежать. Тут несколько вариантов:

- Если BookService упал, вообще ничего не покажем

- Если AuthorService упал, покажем книгу без автора

- Можно кэшировать данные авторов, чтобы при падении брать из кэша

- Можно ставить таймауты: если AuthorService не ответил за 2 секунды, возвращаем книгу и пишем "автор временно
  недоступен"

### Как объединяем ответы

BookService вернет что-то типа:
json

    {
    "id": 1,
    "title": "Книга",
    "authorId": 5
    }

AuthorService вернет:
json

    {
    "id": 5,
    "name": "Автор",
    }

Gateway склеит это в:
json

    {
    "book": {...},
    "author": {...}
    }

Клиент получает готовый кусок данных, не нужно ничего дособирать на фронте.

### Таймауты

Нужно настраивать разумные таймауты для каждого сервиса. Если BookService обычно отвечает за 50 мс, а AuthorService за
100 мс, ставим таймауты с запасом: 200 мс и 300 мс.

### Мониторинг

Важно следить, как часто падают эти агрегирующие запросы. Если AuthorService постоянно тормозит, может, его надо
масштабировать или оптимизировать.
Кэширование

Данные авторов меняются редко. Можно кэшировать ответы AuthorService на Gateway. Тогда при повторных запросах на книги
того же автора не нужно ходить в AuthorService, берем из кэша.
Версионирование

Если поменяется API BookService или AuthorService, придется обновлять логику в Gateway. Это минус, добавляется
связанность.

### Зачем все эти сложности

Фронтенд проще, один запрос вместо двух

Быстрее для пользователя, параллельные запросы экономят время

Меньше нагрузки на сеть, один запрос вместо двух

Централизованная обработка ошибок, не нужно на каждом клиенте писать логику "что делать, если автор не загрузился"

На что смотреть при реализации

WebClient должен быть правильно настроен, пулы соединений, таймауты

Нужно логировать, если один из сервисов долго отвечает

Хорошо бы добавить метрики: сколько времени занимает агрегация, сколько ошибок

Продумать fallback-логику на случай падения сервисов

### Итог

Делаем в Gateway эндпоинт, который параллельно дергает два сервиса, ждет оба ответа, склеивает их и отдает клиенту.
Получается быстрее и удобнее, чем делать два запроса с клиента. Главное, правильно обрабатывать ошибки и не забывать
про таймауты.
